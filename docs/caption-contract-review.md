# 자막 연동 코드 대조

2026-10-20 로컬 코드 기준 정적 검토. AI `221c182`, NestJS `d8fcd5e`, 현재 클라이언트 작업 파일을 비교했다. 실제 배포 환경과 장시간 인식 성공은 별도 검증이 필요하다.

## 1. 수어 요청 검증 — 최신 DTO 반영 확인

| 위치 | 확인한 동작 |
| --- | --- |
| client `useSignLanguage.ts` | 평균 x 순서의 손 슬롯 42개씩 + 어깨 4개 = 88개. x 반전 없이 30프레임 전송 |
| Nest `src/calls/dto/send-frame.dto.ts` | 내부 배열마다 유한한 숫자 88개인지 검사 |
| AI `router/cc.py:400` | `(88,)` 또는 `(N,88)` 배열 허용 |
| AI `util/config.py` | INPUT_SIZE=88, WINDOW_SIZE=30 |

프론트 30×88은 최신 로컬 Nest DTO와 AI 입력 형식에 맞는다. 실제 배포 버전과 ACK는 별도 확인해야 한다.

## 2. 음성 바이너리 형식 불일치

- 프론트 `useSpeechToText.ts`는 MediaRecorder 바이너리(WebM/Opus 우선, 1초 청크)로 수정했다. 재연결마다 녹음기를 새로 만들어 헤더부터 전송한다.
- AI `router/cc_stt.py`는 수신 바이트를 합쳐 `io.BytesIO`로 만들고 `model.transcribe`에 파일 입력으로 넘긴다. raw PCM의 샘플레이트·채널·타입을 지정하거나 파형 배열로 변환하는 처리가 없다.
- AI 테스트 도구 `scripts/stt_streamlit_debug.py`는 오디오 파일 또는 MediaRecorder의 인코딩된 바이너리를 전송한다. 프론트도 MediaRecorder 방식으로 맞췄다.
- 추론 루프는 예외를 `except Exception: continue`로 넘긴다. 따라서 디코딩 오류가 발생해도 연결은 유지되고 자막만 없을 수 있다. 실제 예외 로그 확인이 필요하다.

프론트는 AI 테스트 도구의 전송 방식에 맞췄다. 남은 문제는 AI가 최근 15개 청크만 보관한다는 점이다. 첫 컨테이너 헤더가 제거되면 이후 청크를 독립 파일처럼 디코딩하지 못할 수 있다. AI에서 지속 디코딩 후 PCM 구간을 관리하는 등의 수정이 필요하다. 짧은 발화와 30초 이상 연속 발화를 각각 검증해야 한다. AI 코드는 수정하지 않았다.

## 3. 사용자별 수어 시퀀스 혼합 가능성

- Nest `CallAiService`는 하나의 AI WebSocket에 모든 방·참가자의 프레임을 보낸다.
- AI `/cc`는 WebSocket 연결 하나마다 단일 `seq_buffer`, `pred_history`, `words`, `call_room_idx`를 유지한다.
- 사용자별 시퀀스를 구분하지 않으므로 여러 사람이 전송하면 서로 다른 사람의 동작 이력이 섞일 수 있다. 30프레임 단위 전송만으로 예측 이력과 문장 버퍼까지 분리되지는 않는다.
- AI 연결을 통화 세션·발화자 단위로 분리하거나 메시지에 발화자 ID를 넣고 AI 상태를 해당 키로 관리해야 한다.

## 4. 단어 출력과 디버그 로그

- AI는 `type: word` 외에 `type: sentence`와 디버그 응답도 보낸다.
- 출품 시 문장화 없이 단어를 출력하기로 했으며 최신 AI는 LLM 문장 재작성을 제거했다. Nest는 `word`만 전달한다.
- 최신 Nest는 구조화된 번역 로그와 10초 단위 relay 통계를 남긴다.
- `debug=1`로 AI에 연결하지만 디버그 응답을 버리므로 인식 실패 이유가 브라우저에 도착하지 않는다. 서버 로그에 기록하는 것이 우선이다.

## 5. 손 감지와 AI 유효 프레임은 다름

- AI는 어깨 두 점의 거리 0.1 이상, 전체 고유 좌표 수 10개 이상, 한쪽 손의 고유 좌표 수 5개 이상 등을 검사한다.
- 30프레임 중 유효 프레임이 최소 24개여야 예측 조건을 만족한다.
- AI `prepare_sequence`에서 어깨 중심 이동·어깨 간 거리 스케일링 및 설정에 따른 시퀀스 정규화를 수행한다. 프론트에서 같은 정규화를 중복 적용하면 안 된다.
- 브라우저의 `손 감지됨`은 손 랜드마크 존재 여부만 확인하므로 위 조건을 보장하지 않는다. 양손과 어깨를 화면 안에 유지해 테스트한다.

## 검증 순서

1. Nest DTO 수정 후 `send_frame` ACK의 `ok: true`, `accepted: true` 확인.
2. 우선 한 사람만 카메라를 켜 AI 디버그의 유효 프레임·예측 결과 확인.
3. AI `word` → BFF `frame_translation` → 자막 표시를 동일 방 번호로 추적.
4. 두 사람 동시 입력 전 AI 세션 분리 확인.
5. STT 형식 통일 후 마이크만 켜 `/cc_stt` 바이너리 수신·디코딩·텍스트 응답 확인.

직접 STT 결과는 본인 화면에 표시하고 기존 `/chat`의 `send_message`로 같은 통화방에 전달한다. `[gesture:stt:v1]` 메시지는 수신 프론트에서 일반 채팅 대신 음성 자막으로 표시하며 서버가 부여한 사용자 ID로 발화자를 찾는다. 긴 텍스트는 분할·재조립하고 중복은 제거한다. 연결이 끊겼을 때는 오래된 자막을 재전송하지 않는다. 음성 바이너리는 계속 AI에 직접 전송한다. 모든 참가자가 최신 프론트를 사용해야 하며 구버전 프론트에는 내부 메시지가 채팅으로 보일 수 있다.

## 프론트 전송 간격 측정

실제 카메라를 연결한 브라우저에서의 측정값은 아직 없다. 자동 테스트 실행시간은 카메라 FPS나 배치 간격이 아니다.

1. 개발자 도구 Console에서 `localStorage.setItem('gesture:caption-debug', '1')` 실행.
2. Console의 로그 수준에서 Verbose/상세를 켜고 통화방에서 카메라를 켠다.
3. 수어를 30초 이상 수행하고 `[Caption] sign_batch` 및 `[Caption] ai_request`를 수집한다.
4. `sign_batch.intervalMs`는 실제 추론 결과 30개를 모아 콜백에 전달한 간격이다. 첫 값은 null이며, `captureSpanMs`는 해당 배치의 첫 결과부터 마지막 결과까지 시간이다.
5. `ai_request.atMs`는 요청 시도 시점, `elapsedMs`는 ACK 완료/실패까지 걸린 시간이다. `accepted` 사이 atMs 차이가 클라이언트에서 확인 가능한 성공 요청 간격이다. 정확한 AI 도착 간격은 서버 수신 로그가 필요하다.
6. `skipped_pending_or_not_ready`는 ACK 대기 또는 미준비 상태로 전송하지 않은 배치이다. ACK 대기 중 새 배치를 버리는 현상을 회귀 테스트로 재현했다. 무제한 큐는 실시간 지연을 누적시키므로 추가하지 않았다.
7. 종료 후 `localStorage.removeItem('gesture:caption-debug')` 실행.

개선안: 간격이 1초를 초과하면 서버 타임아웃을 실측 최대 간격과 네트워크 여유에 맞춰 늘리거나, 프레임을 더 작은 묶음으로 보내고 서버에서 30개를 누적하는 계약으로 변경한다. 현재 요청대로 30프레임 배치는 유지한다. ACK가 길다면 BFF가 입력 검증·접수 직후 ACK하고 추론 결과는 별도 이벤트로 보내는지 확인한다. 중복 프레임 복제로 30개를 채우면 학습 시계열을 왜곡하므로 사용하지 않는다.

`ignore_hands_down=1`은 프론트에 없고 Nest의 AI 연결 주소에 있다. 최신 팀 합의에 따라 유지한다. 백엔드·AI 코드는 수정하지 않았다.

한 손만 있고 어깨가 검출되지 않으면 슬롯 기준을 알 수 없어 손 슬롯을 0으로 채운다. 화면 중심 등 임의 기준은 사용하지 않는다. 두 손은 평균 x 순서이며 동일 평균 x에서는 기존 검출 순서를 유지한다.
